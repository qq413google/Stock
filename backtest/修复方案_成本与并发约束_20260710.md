# 回测修复方案：交易成本 + 组合级并发约束

> 背景：`回测研究_5项挤水分_20260710.md`（研究A/B/C/D/E）已完成并经人工复核——数据未造假、算术自洽，但研究A/B/C共用的回测引擎（`lib.js` 的 `simulate()`+`metrics()`）有3处未披露的方法论缺口，会让具体数字失真（不一定推翻方向，但精度不可信）。本方案只修复这些缺口，**不需要重新设计策略/规则**。
>
> 执行者只需改 `backtest/lib.js` + `backtest/studies.js`，跑出新数字，和旧数字对比。**研究D、研究E不受影响，不用碰。**

---

## 问题回顾（为什么要修）

看 `backtest/lib.js` 的 `simulate()` + `metrics()`：

1. **没扣交易成本**：`pnl = (exit - entry) * shares`，没减手续费/印花税。项目自己的 `references/risk-management.md` 十一节写着"往返约0.15%"。研究B的核心结论"严格买点 +0.1%/笔"本身就比0.15%摩擦成本还小——扣完成本可能由正转负。
2. **回撤(mdd)不是真实组合级回撤**：`studies.js` 里21只股票是"一只股票的信号跑完、结果数组`push`进去，再跑下一只股票"（各股票内部按时间顺序，但股票之间是拼接、不是按真实日期归并）。`metrics()` 对着这个拼接后的数组算最大回撤，相当于假设"每只股票各自独立、无限本金、互不影响"，不是"5万账户、同时最多3只"的真实约束。研究C那句"≤180回撤8.1% vs >180回撤37.9%"，方向大概率对，但数字不是真实组合回撤。
3. **成交价假设偏乐观**：买入按信号当天收盘价成交（现实要等收盘确认，次日开盘才能下单，可能已跳空）；止损按精确止损价成交（`r.l<=stop`就假设能卖在stop价，没算跳空低开砸穿止损的情况）。

---

## 修复目标

只改 A、B、C 三个研究用到的回测引擎，让它：
1. 扣掉往返0.15%交易成本；
2. 用**真实组合级模拟**（同时最多3个仓位、单一5万账户、按真实日期顺序推进）算出交易记录，再算 mdd/pf；
3. 保留旧引擎/旧结果不删，新旧并列输出，方便对比改动前后差多少。

**不改**：研究D、E的方法（它们用 `fwdReturn` 直接算未来收益，不经过 `simulate()`/`metrics()`，不受上述问题影响，结果保持原样）。也不改交易信号定义本身（`gate`/`banned`/`buyPoints`/`strictBuy`/`looseBuy`/`mrBuy`/`anyTrendBuy` 这些函数不用动）。

---

## 具体实现

### 1. 交易成本（改 `lib.js`）

在计算 pnl 的地方（新引擎里，见下）加成本扣减：

```js
const COST_RATE = 0.0015; // 往返0.15%，来自 risk-management.md 十一节
function applyCost(entry, exit, shares) {
  const notional = (entry + exit) / 2 * shares;
  return notional * COST_RATE; // 扣减金额，从 pnl 里减掉
}
```

`pnl = (exit - entry) * shares - applyCost(entry, exit, shares)`；`pnlPct` 同步扣（`pnlPct = pnl / (entry * shares)`，用扣完成本后的pnl重算，不要只扣原始pnlPct）。

### 2. 组合级并发模拟（`lib.js` 新增函数，不要改掉原 `simulate()`——D/E用不到它，但别的地方可能引用，保留兼容）

新增 `simulatePortfolio(stocks, buyFn, opts)`：

**输入**：`stocks` = `[{name, rows}, ...]`（每只股票已算好指标的行数组，字段同现有 `rows`）；`buyFn` = 策略函数（`strictBuy`/`looseBuy`/`mrBuy`/`anyTrendBuy` 之一）；`opts.maxConcurrent`（默认3）。

**算法**（伪代码）：

```
1. 建立"主日历"：把所有 stocks 的 rows.date 取并集，升序排序 → dates[]
2. 给每只股票建 date→rowIndex 的映射（Map），方便按日期查该股票当天的行
3. openPositions = []   // 最多 maxConcurrent 个，元素含 {stockName, entry, stop, shares, kind, highest, takeProfit, entryDate}
4. trades = []          // 按真实收盘日期顺序追加，最终就是"真实组合级交易序列"
5. missedByCapacity = 0 // 因为3个仓位已满、错过的合法信号数(用于报告)

6. for date of dates (按时间升序):
     a. 【先处理平仓】对 openPositions 里的每个仓位:
          取该股票在 date 的行 r（如果这只股票当天没有行，跳过，等下一个有数据的交易日再判断）
          按原 simulate() 里同一套退出逻辑判断(target/stop/hardstop/trail/timeout)
          若触发退出:
            pnl = (exit-entry)*shares - applyCost(entry,exit,shares)
            trades.push({stock, entryDate, exitDate: date, entry, exit, shares, pnl,
                         pnlPct: pnl/(entry*shares), kind, reason})
            从 openPositions 移除该仓位 (释放一个名额)

     b. 【再处理开仓】对每只"当前没有持仓"的股票(且它在 date 当天有行数据):
          sig = buyFn(该股票的rows, date对应的rowIndex)
          if sig 存在:
            if openPositions.length >= opts.maxConcurrent(默认3):
                missedByCapacity += 1   // 记录被容量卡掉的信号，不开仓
                continue
            按原 simulate() 里同一套仓位计算规则(≤180元用止损反推手数、>180元固定1手、单手≤1.8万)算 shares
            若 shares >= 100: openPositions.push({stockName, entry, stop, shares, kind, highest:entry,
                                                    takeProfit, entryDate: date})

7. 循环结束后，openPositions 里如果还有仓位(窗口末尾未平仓)，按最后一天收盘价强制平仓，
   reason='window_end'，同样计入 trades 并扣成本。

8. 返回 { trades, missedByCapacity }
```

**关键点**：
- 开仓/平仓判断都要按 `dates[]` 的真实时间顺序推进，**不能按股票分组跑完一只再跑下一只**——这是本次修复的核心，否则 mdd 还是假的。
- `maxConcurrent` 默认设 3（对应账户规则"同时持仓≤3只"）。如果想同时验证"单赛道≤50%"约束，可以加一个可选的 `sectorCap` 参数（每只股票的 `赛道` 字段来自 `watchlist.json`），但这不是本次必做项，做不做都行，做的话在报告里单独说明。
- `metrics()` 这个函数本身不用改——它现在拿到的 `trades` 数组已经是按真实日期顺序排列的了，所以里面算 mdd 的那段代码（`for (const t of trades) { eq += t.pnl; ... }`）自动就是对的，不需要动。

### 3. `studies.js` 改法

研究A、B、C 里，把：
```js
for (const s of wlLong) { trend.push(...L.simulate(s.rows, strictBuy, { name: s.name })); ... }
```
这种"逐股票跑`simulate()`再`push`拼接"的写法，换成一次性调用：
```js
const { trades: trend, missedByCapacity } = L.simulatePortfolio(
  wlLong.map(s => ({ name: s.name, rows: s.rows })), strictBuy, { maxConcurrent: 3 }
);
```
A、B、C 三段都这样改（用各自对应的策略函数和股票列表：A用`wlLong`+`strictBuy`/`mrBuy`/`combinedBuy`，B用`wlFlow`+`strictBuy`/`looseBuy`，C用`uni`(含高价龙头)+`anyTrendBuy`）。

研究D、E的代码**不动**。

### 4. 输出要求

1. 新结果写到 `backtest/results_v2.json`，**不要覆盖**原 `results.json`（要保留旧的做对比）。
2. 新报告文件 `backtest/回测研究_成本与并发修正版_20260710.md`，格式：
   - A/B/C 三节，每节一张"旧引擎 vs 新引擎"对比表：n、胜率、期望/笔(¥和%)、盈亏比、最大回撤——旧值直接从现有 `results.json` 读，不用重跑旧引擎。
   - 每节额外报告 `missedByCapacity`（因3仓位已满错过多少个原本合法的信号）——这是新增的、之前完全没有的信息，很重要，能看出"3仓位约束"平时到底卡掉了多少交易。
   - D、E 两节写"沿用原结果，本次未改动"，把原数字抄一遍即可，不用重跑。
   - 结尾一段：三个原结论（研究A搁置MR / 研究B买点加分 / 研究C保留≤180约束）修正后是否还成立，哪个被扣成本/加约束后翻车了。

### 5. 验收标准（跑完必须自查，过不了就是哪里写错了）

对 A/B/C 新结果各做一次算术自洽性检查（和原报告复核时一样的方法）：
- `exp ≈ winRate × avgWin + (1-winRate) × avgLoss`（容差 ±1元）
- `pf ≈ grossWin / grossLoss`（grossWin/grossLoss 自己从 trades 里按 wins/losses 分组算出来对一遍）
- 遍历新 `trades` 数组，**断言任意时刻同时持仓数不超过3**（可以在模拟循环里维护一个计数器，跑完打印最大同时持仓数，应该 ≤3，如果代码写对这个应该正好等于3或更小）
- `pnlPct` 用扣成本后的 `pnl` 重新算的，不是拿原始（未扣成本）pnlPct
