## 缺口1：研究C把≤180和>180混进同一个共享3仓位池，再事后拆分——不公平，且样本薄

现状（`studies.js` 第183-203行）：`anyTrendBuy` 用 `useCap:false` 跑**一次**组合模拟，23只股票（含5只高价龙头）混在一起抢同一批3个名额，跑完才按 `entry<=180` / `entry>180` 拆成两组统计。

问题：现实中没人会"一边执行≤180规则，一边让>180的信号跟你抢名额"——你要么完全遵守≤180（那些信号从来不会进入候选池），要么完全不设限（任何信号都能抢）。这是两个互斥的世界，应该各自跑一次、各自独享3个名额，而不是混合后拆分。而且现在拆出来的 `gt180` 只剩 **n=7笔**，样本太薄，不能支撑"高价股更差"这个结论。

**修法**：把"一次模拟+事后拆分"改成**两次独立模拟**，直接对比整体表现：

```js
// 研究C改法（替换现有 187-203 行的写法）：
const stocks = uni.map(s => ({ name: s.name, rows: s.rows }));

// 场景A: 严格执行≤180约束(真实策略) —— useCap:true, 高价信号永远不进候选池,不占用名额
const capped = L.simulatePortfolio(stocks, anyTrendBuy, { useCap: true });

// 场景B: 不设价格限制(假设约束不存在) —— useCap:false, 任何信号都能抢同样的3个名额
const uncapped = L.simulatePortfolio(stocks, anyTrendBuy, { useCap: false });

const mCapped = L.metrics(capped.trades);
const mUncapped = L.metrics(uncapped.trades);

// 仅做描述用途: 从 uncapped 的成交结果里看有多少笔是高价股("抢到名额"的高价股，非全部候选)
const gt180InUncapped = uncapped.trades.filter(t => t.entry > L.PRICE_CAP);
```

**结论怎么下**：直接对比 `mCapped` vs `mUncapped` 整体的 期望/笔、pf、mdd、累计——这才是"要不要保留≤180约束"这个决策真正对应的两个可比场景。`gt180InUncapped` 只作为"解释uncapped为什么和capped不一样"的辅助信息，**不再单独对它下"高价股是否有edge"的结论**（样本太小，且它是在跟低价股抢名额的动态过程里产生的，不是独立可比的东西）。

## 缺口2：抢3个名额时，"谁先拿到"按 `watchlist.json` 列表顺序算，不是按信号质量——引入了跟策略无关的偏向

现状（`lib.js` `simulatePortfolio` 第222-247行）：每天开仓判断是 `for (const sm of stockMaps)` 顺序遍历，谁先在列表里出现、谁先抢到名额。`watchlist.json` 里光通信/半导体在前，医药股(恒瑞/药明/康龙/华东/泰格)在最后——这意味着医药股在任何"当天多只票同时触发信号"的场景下，**结构性地、每次都更容易抢不到名额**，跟这些票的信号质量毫无关系。

**修法**：把 `simulatePortfolio` 的开仓逻辑从"遍历到谁就直接判断谁"改成"当天先收集所有候选信号，按优先级排序，再从高到低顺序占名额"。

在 `lib.js` 里改 `simulatePortfolio` 的 3b 步骤（第221-247行）：

```js
// 3b. 收集当天所有候选信号(不再遍历到就立即决定，先收集再排序)
const candidates = [];
for (const sm of stockMaps) {
  if (heldSet.has(sm.name)) continue;
  const idx = sm.map.get(date);
  if (idx === undefined) continue;
  const sig = buyFn(sm.rows, idx);
  if (!sig) continue;
  if (USE_CAP && sig.entry > PRICE_CAP) continue;
  candidates.push({ sm, idx, sig });
}

// 按优先级排序(默认: 主力净占比高的优先; 拿不到资金流数据的排最后; 相同优先级保持原列表顺序稳定排序)
const priorityFn = opts.priorityFn || ((r, i) => (isNaN(r[i].mainRatio) ? -999 : r[i].mainRatio));
candidates.sort((a, b) => priorityFn(b.sm.rows, b.idx) - priorityFn(a.sm.rows, a.idx));

// 按排序后的顺序占名额，占不到的计入missedByCapacity
for (const { sm, idx, sig } of candidates) {
  if (openPositions.length >= MAX_CONCURRENT) { missedByCapacity++; continue; }
  let stop = sig.stop;
  if (!(stop > 0) || stop >= sig.entry) continue;
  stop = Math.max(stop, sig.entry * HARD_STOP);
  const stopDist = sig.entry - stop;
  if (stopDist <= 0) continue;
  let shares;
  if (sig.entry <= PRICE_CAP) {
    shares = Math.floor(RISK_YUAN / stopDist);
    shares = Math.min(shares, Math.floor(18000 / sig.entry));
    shares = Math.max(shares - (shares % 100), 100);
  } else {
    shares = 100;
  }
  if (shares < 100) continue;
  openPositions.push({ stock: sm.name, entry: sig.entry, stop, shares, kind: sig.kind,
    highest: sig.entry, takeProfit: sig.takeProfit || null, entryDate: date, entryIdx: idx });
  heldSet.add(sm.name);
}
```

`priorityFn` 通过 `opts.priorityFn` 可传可不传（不传就用默认的"主力净占比优先"）——这样同一个引擎可以跑出"按信号质量排序"和"按原始列表顺序"两个版本对比。

**注意**：`mainRatio` 字段只在120天资金流窗口内有值；研究C用的是完整K线(可能超出120天窗口)，超出部分 `mainRatio` 会是 `NaN`，此时按上面公式排到最后，属于预期行为（没有资金流数据佐证的信号，优先级最低，合理）。
